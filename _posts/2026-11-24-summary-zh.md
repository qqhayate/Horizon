## [从零自研的浏览器引擎 Ladybird 进入 Alpha 阶段](https://ladybird.org/posts/alpha/) ⭐️ 9.0/10

Ladybird 浏览器基于完全自研的独立引擎（而非 Chromium 或 Gecko），现已正式进入 Alpha 阶段，能够正确渲染大量真实网站。公告发布后，有用户实测反馈 Proxmox 的 NoVNC 远程控制台视图以及内容繁重的新闻网站都能正常加载和显示。 一个真正全新的浏览器引擎能达到可用的 Alpha 阶段，是几十年来未曾出现过的里程碑——目前整个 Web 由少数几个引擎主导，而每个引擎背后都是一家以广告为收入来源的公司。如果 Ladybird 持续成熟，它有望为 Web 标准的实现方式重新引入真正的竞争与独立性。 该项目主要以 C++ 编写，并正在逐步向 Rust 迁移；同时它放弃了部分早期自研库，改用 SQLite、Skia 等生产级组件，从而显著提升了兼容性与稳定性。早期测试者指出渲染基本正确，但页面滚动仍略显卡顿，开发团队也提醒该版本面向开发者而非普通日常用户。

hackernews · janvdberg · 11月23日 16:13 · [社区讨论](https://news.ycombinator.com/item?id=50614249)

**背景**: 浏览器引擎是负责解析 HTML、CSS 与 JavaScript 并将其呈现为屏幕画面的核心软件；如今几乎所有浏览器都建立在 Blink（Chrome、Edge）、Gecko（Firefox）或 WebKit（Safari）之上。Ladybird 最初是 Andreas Kling 发起的 SerenityOS 业余操作系统的一部分，后来独立出来，成为一个由非营利基金会支持的独立浏览器。从零构建引擎极其困难，因为现代 Web 依赖多年积累的标准合规性和各种兼容性细节，这正是独立引擎如此稀少的原因。

## [Anthropic 称 Claude 发现 VP≠VNP 并公开 Lean 4 证明](https://github.com/anthropics/formal-math/blob/main/vp-vnp/README.md) ⭐️ 9.0/10

Anthropic 于 11 月 24 日公开了题为《VP ≠ VNP over every field》的论文及 Lean 4 形式化证明，称结果由内部研究用 Claude 模型发现，论文与代码均由 AI 撰写。论文声称给出了哈密顿圈多项式的超多项式算术电路下界，并据此推出 VP 是 VNP 的真子类。 如果该结论通过审阅，它将解决 Valiant 于 1979 年提出的代数复杂度猜想——在每个域上 VP ≠ VNP，这既是长期未解难题，也是检验 AI 发现数学能力的重要案例。其影响主要集中在代数复杂度与形式化验证领域，而不会直接解决 P 与 NP 问题，因为该论证针对的是算术电路而非布尔计算。 仓库称已通过三条标准公理审计，并使用独立内核 nanoda 复核，除预留文件外没有 sorry。但目前尚无人类数学家完整通读证明，Lean 本身无法确认形式化陈述与所声称的命题一致，附录 Q 列出了出入之处，该工作仍待独立审阅。

telegram · zaihuapd · 11月24日 06:02

**背景**: Valiant 将 VP 与 VNP 定义为 P 与 NP 的代数对应物：VP 包含可由多项式大小算术电路计算的多项式族，而 VNP 包含永久式等被认为难算得多的多项式族。VP 与 VNP 问题追问的是，在给定域上这两个类是否不同；新主张称这种分离在每个域上都成立。Lean 4 是一种证明助手，其内核负责检查形式化证明；sorry 是未完成证明的占位符，而 nanoda 等独立检查器提供了内核的第二个实现，用于发现潜在缺陷。

## [智谱发布 GLM-5.4：首个循环 Transformer 模型，主打通用编程](https://z.ai/blog/glm-5.4) ⭐️ 8.0/10

智谱（Z.ai）发布了 GLM-5.4，称其为首个旗舰级“循环 Transformer”（loop transformer）模型：它不再为每一层堆叠独立的权重，而是让同一个共享层块反复迭代运行。官方将该模型定位在“通用编程”方向，并宣称它能在不增加参数量的情况下获得相当于 2T–3T 参数模型的推理深度。 如果循环架构确实奏效，实验室就能在不按比例增加参数量和显存流量的前提下获得更强的推理深度，从而把前沿竞争的一部分从“堆规模”转向“拼架构”。这次发布同样重要的另一点是，智谱公开了足以被外界研究的架构细节，社区成员认为这与西方实验室的封闭做法形成鲜明对比。 早期试用者在接入上遇到了麻烦：该模型既不在 OpenRouter 上，也不在 Z.ai 的标准 API 套餐中，用户必须改用 Coding Plan 才能拿到可调用它的 API 密钥。社区测试者还反映模型存在严重的“马拉松式思考”，即便是概念上很简单的任务也会进行冗长的自我反复检查，完成时间明显长于前沿模型。

hackernews · foohis · 11月23日 10:06 · [社区讨论](https://news.ycombinator.com/item?id=50609685)

**背景**: 标准 Transformer 由一叠层组成，每层都有各自的注意力权重和前馈权重；推理时每一层都要从 HBM 显存搬到芯片上、计算一次再换出，因此显存带宽成为生成 token 的首要瓶颈。循环 Transformer 则让同一组共享权重迭代运行多次，结构上更接近一个 for 循环，而不是把不同层平铺展开，于是每搬运一个字节的权重就能完成更多计算。这类权重共享思路在研究中已存在多年（例如 Universal Transformer 以及 ALBERT 式分解共享），但 GLM-5.4 的特殊之处在于它是围绕这一思路打造的旗舰商用模型。

## [Stalwart 1.2.0 宣称可直接替代 Microsoft Exchange](https://stalw.art/blog/microsoft-exchange-replacement/) ⭐️ 7.0/10

Stalwart 发布了 1.2.0 版本，并在博客中宣布这款开源邮件与协作服务器如今可以作为 Microsoft Exchange 的直接替代品（drop-in replacement），文中指出二十多年来企业邮件几乎等同于 Exchange 服务器加 Outlook 客户端的组合。这一说法将该 Rust 编写的服务器定位为 Exchange 部署的自托管替代方案，而不只是又一个 IMAP/JMAP 邮件服务器。 Exchange 是少数几个仍由专有、高授权成本软件把持的邮件基础设施重镇之一，因此一个可信的开源替代方案对所有希望摆脱 Microsoft 365 按用户订阅计费的自托管管理员和组织都意义重大。它对整个开放邮件生态同样重要：任何延续 Exchange 式客户端与协议的工具，既可能降低迁移门槛，也可能延长微软的协议锁定。 Stalwart 是一款一体化协作服务器，支持 JMAP、IMAP4、POP3、SMTP、CalDAV、CardDAV 和 WebDAV，内置垃圾邮件与钓鱼防护，并提供日历、联系人和共享文件功能。评论者指出，“直接替代”这个标签承载了过多期待：兼容 Exchange 风格的客户端本身并不涵盖德国 GoBD 等法规所要求的合规归档能力，而据称该项目在标准版和开源版本中并未提供这一功能。

hackernews · shaunpud · 11月23日 22:32 · [社区讨论](https://news.ycombinator.com/item?id=50620349)

**背景**: Microsoft Exchange 长期主导企业邮件与日历服务，Outlook 则是与之配套的客户端，两者通过微软自有协议紧密耦合，历史上很难只替换其中一环。Stalwart 是一款用 Rust 编写的开源邮件与协作服务器，目标是在单一可执行程序中实现 JMAP、IMAP、CalDAV、CardDAV 等现代开放标准。宣布兼容 Exchange 意味着，组织原则上可以保留现有的 Outlook 用户和邮件流，只在底层用 Stalwart 取代 Windows Server 与 Exchange 授权。
